# Module 0, Lesson 4: Create the First Git Checkpoint

**Status:** Draft blueprint; not implemented or validated

## Learning outcome

Create a local Git repository for the Godot project and record its first
reviewed checkpoint.

## Finished result

At the end of this lesson:

- The `2D Platformer` project folder is a local Git repository on `main`.
- Godot's generated cache is excluded from Git.
- Project source files are included in the first commit.
- The latest commit is named `Create empty Godot project`.
- `git status` reports a clean working tree.
- Nothing has been uploaded to GitHub or another online service.

## Why this comes next

Git is ready, but the project has no recorded recovery point. Creating the
first checkpoint before Codex begins editing project files gives the learner a
known working state for later comparison and recovery.

This lesson teaches one practical cycle: inspect, stage, review, commit, and
verify. Online backup and advanced recovery come later.

## Before you start

- Module 0, Lessons 1 through 3 are complete.
- `git --version` works in a newly opened PowerShell window.
- Git has the intended author identity and `main` default branch.
- The `2D Platformer` project opens without errors.
- The project folder is not already inside another Git repository.

## Course decisions

| Decision | Course choice | Why |
| --- | --- | --- |
| Repository location | The Godot project root | Keeps history beside `project.godot` without tracking unrelated parent folders. |
| Branch | `main` | Matches the default configured in Lesson 3. |
| Version-control metadata | Generated by Godot, then inspected | Provides suitable ignore and line-ending rules without treating them as a black box. |
| Staging | Stage the small empty project together | The complete staged list is short enough for a beginner to review. |
| First commit | `Create empty Godot project` | Describes the working result recorded by the snapshot. |
| Online backup | Not included yet | The learner understands the local model before adding accounts and remotes. |

## New concepts

- **Repository:** A project folder whose history is managed by Git.
- **Working tree:** The current files visible in the project folder.
- **Tracked file:** A file Git includes in project history.
- **Untracked file:** A visible file that Git has not yet been asked to include.
- **Ignored file:** A file Git has intentionally been told not to include,
  usually because it is generated or private.
- **Staging area:** The reviewed set of changes prepared for the next commit.
- **Commit:** A named snapshot of staged project changes.

A local commit is not automatically an online backup. This checkpoint exists
only on this computer until GitHub is introduced in Lesson 5.

## Lesson steps

### Part 1: Generate and inspect Godot's Git metadata

1. Open the `2D Platformer` project in Godot.
2. Open **Project → Version Control → Generate Version Control Metadata**.
3. Choose **Git** when Godot asks for the version-control system.
4. Confirm that Godot creates `.gitignore` and `.gitattributes` in the project
   root.
5. Right-click `res://` in the FileSystem dock and select **Open in File
   Explorer**.
6. Open `.gitignore` and `.gitattributes` in a text editor.
7. Confirm that `.gitignore` excludes at least:

   ```gitignore
   .godot/
   *.translation
   ```

8. Confirm that `.gitattributes` keeps text files on consistent LF line
   endings.
9. Confirm that important source files are not ignored, including:
   - `project.godot`
   - Godot scenes such as `.tscn`
   - GDScript files such as `.gd`
   - Godot resources such as `.tres`
   - `export_presets.cfg` when it is created later
10. Save only if a verified rule is missing or incorrect, then close the text
    editor.

Godot 4.1 and later stores confidential export options inside the ignored
`.godot/` folder. `export_presets.cfg` contains useful export configuration and
can remain in project history.

### Part 2: Initialize and inspect the repository

1. Close Godot so its files are stable during the first checkpoint.
2. In the open File Explorer window, select the address bar.
3. Type `powershell` and press **Enter**. PowerShell opens in the project
   folder.
4. Confirm that the prompt path is the folder containing `project.godot`.
5. Initialize the repository on `main`:

   ```powershell
   git init -b main
   ```

6. Inspect the repository:

   ```powershell
   git status
   ```

7. Confirm that Git reports `main` and lists the expected project files as
   untracked.
8. Confirm that `.godot/` is absent from the files offered for tracking.

The hidden `.git` folder created by `git init` stores Git's local history and
settings. Do not edit, move, or delete its contents manually.

### Part 3: Stage, review, and commit

1. Stage the small empty project:

   ```powershell
   git add .
   ```

2. Review exactly what is staged:

   ```powershell
   git status
   git diff --cached --stat
   ```

3. Confirm that only expected project source and metadata are staged.
4. Confirm that generated `.godot/` files and private credentials are absent.
5. Create the first commit:

   ```powershell
   git commit -m "Create empty Godot project"
   ```

6. Verify the checkpoint:

   ```powershell
   git status
   git log --oneline -1
   ```

7. Confirm that the working tree is clean and the latest message is
   `Create empty Godot project`.

## Understand the basic Git cycle

The normal checkpoint cycle in this course is:

`inspect → stage intended changes → review → commit → verify`

- `git status` shows the current state.
- `git add` prepares chosen content for the next snapshot.
- `git diff --cached` reviews what is prepared.
- `git commit` records the prepared snapshot.
- A second `git status` shows what remains afterward.

Staging is not saving, uploading, or committing. It is the review boundary
between current work and the next recorded snapshot.

## Practical Git practices and tips

- Run `git status` before and after every commit.
- Review the staged-file list before committing.
- Use commit messages that describe the working result.
- Commit after a small result works, not after many unrelated changes.
- Never commit passwords, tokens, private keys, or export credentials.
- Do not use destructive recovery commands from AI without understanding the
  exact affected files and changes.
- A local commit protects against editing mistakes, not drive loss.

## Role of AI

Codex is deliberately not connected to the project yet. The learner first
creates and recognizes the manual safety boundary Codex will use.

Later, Codex can summarize status, explain a diff, help group related changes,
and propose a commit message. The learner must still inspect staged changes
and explicitly approve commits. Codex should not publish or discard history
without a clear request.

## Modularity checkpoint

No gameplay module is changed. Future module addition, customization, and
removal can each be captured as an independent checkpoint.

There are no Inspector customization points in this lesson.

## Learner exercise

Without reading the commands again:

1. Run `git status` and identify the branch.
2. Run `git log --oneline -1` and locate the commit message.
3. Explain untracked, ignored, staged, and committed files.
4. Explain why `.godot/` is ignored.
5. Explain why this checkpoint is useful but is not yet an online backup.

## Common mistakes

| Problem | What to do |
| --- | --- |
| PowerShell opened in the wrong folder. | Reopen it from the folder containing `project.godot`. |
| `git init` was run in a parent folder. | Do not commit. Confirm the intended root and get help removing only the mistaken Git metadata. |
| `.godot/` appears in the staged list. | Stop before committing and correct `.gitignore`. |
| Important project files are missing. | Check whether an ignore rule is too broad before committing. |
| `export_presets.cfg` is ignored. | Remove that obsolete rule for Godot 4.1 or later; keep confidential export data ignored. |
| Git asks for an author identity. | Return to Lesson 3, configure the intended identity, and retry. |
| The working tree is not clean afterward. | Run `git status` and inspect what was not included; do not discard it automatically. |
| The learner expects GitHub to contain the project. | Explain that the repository and commit are still local. |
